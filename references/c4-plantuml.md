# Diagram standards — PlantUML (Phases 0 and 4)

All ESDD diagrams are PlantUML source, one diagram per file, stored in
`specs/<slug>/diagrams/`. design.md files reference them — never inline
hundreds of lines of diagram source in a design doc.

Every file starts with the base theme (adjust depth as needed):

```plantuml
!include ../../assets/base-theme.puml
```

C4 diagrams additionally include exactly one C4-PlantUML level file:

```plantuml
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Context.puml
```

## File naming

`<n>-<kind>-<name>.puml` — `1-context-shop.puml`, `2-container-shop.puml`,
`3-component-checkout.puml`, `4-code-pricing.puml`,
`5-sequence-checkout.puml`, `5-activity-order-fulfilment.puml`,
`5-state-order.puml`, `6-er-catalog.puml`.

Level 1–2 (Context, Container) normally live in the SHARED `.esdd/design.md`
and its `specs/_shared/` diagram dir; a spec only adds them when it changes
the workspace boundary. Levels 3–6 are spec-local.

## C4 quick reference

```plantuml
' Context
Person(customer, "Customer", "Buys things")
System(shop, "Shop", "Sells things")
System_Ext(payments, "Payment provider", "Takes money")
System_Boundary(b, "Shop") { ... }
Rel(customer, shop, "Places orders", "HTTPS")
Rel(shop, payments, "Charges cards", "HTTPS")

' Container
Container(web, "Web app", "TypeScript, React", "Serves UI")
ContainerDb(db, "Primary DB", "Postgres 16", "System of record")
ContainerQueue(queue, "Event bus", "RabbitMQ", "Domain events")
Rel(web, db, "Reads/writes", "SQL")

' Component
Component(controller, "OrderController", "Handles order HTTP requests")
Component(pricing, "PricingEngine", "Computes prices per QAS-1")
```

C4-PlantUML relations support direction and technology: `Rel(a, b, "uses",
"JSON/HTTPS")`, `Rel_D`, `Rel_U`, `Rel_L`, `Rel_R`.

## Dynamic views

```plantuml
' Sequence
participant "Web app" as web
participant "PricingEngine" as pricing
web -> pricing : price(cart)
pricing --> web : Price(total, currency)

' Activity
start
:Validate cart;
if (in stock?) then (yes)
  :Reserve items;
else (no)
  :Backorder;
endif
stop

' State machine
[*] --> Draft
Draft --> Placed : payment confirmed
Placed --> Shipped : dispatch
Shipped --> [*]
```

## ER with crow's foot (extended notation)

Cardinality is written with two-character arcs on each side of the
relationship:

```
|o   zero or one
||   exactly one
}o   zero or many
}|   one or many
```

```plantuml
' one customer places zero-or-many orders;
' each order belongs to exactly one customer
entity Customer
entity "Order" as O
Customer ||--o{ O : places

' many-to-many with join entity
O }o--o{ Product : contains
entity "OrderLine" as OL
O ||--|{ OL
OL }o--|| Product
```

Modifiers combine as `<left><right>--<right><left>`: `||--o{`, `}o--o|`,
`|o--|{`, etc. Read each side from the outside in: first character is the
minimum, second the maximum nearest the entity.

## Rules that keep diagrams cheap

- One diagram per file, one concern per diagram. If a diagram needs a
  scroll, split it — the token budget applies to reading diagrams too.
- Diagrams are generated by a subagent from the design.md section they
  illustrate; the orchestrator checks the render, not the source.
- Names in diagrams must match names in design.md and in task briefs.
  An element renamed in prose but not in the diagram invalidates both.
